## Klassenueberblick
`checkanswers` ist der Orchestrator des gleichnamigen Frameworks zur Nachvalidierung von Buchungsantworten (Use-Case: User automatisch aus Optionen entfernen, wenn sie keinen Zugriff mehr haben). Es definiert die Konstanten fuer Checks (`CHECK_ALL`, `CHECK_COURSE_ENROLLMENT`, `CHECK_CM_VISIBILITY`) und Actions (`ACTION_DELETE`), erzeugt pro Buchungsoption einen Adhoc-Task und fuehrt zur Laufzeit ueber `core_component`-Namespace-Discovery die passenden Check-/Action-Klassen aus. Persistenz: liest `booking_options`/`booking`/`course_modules`/`context`/`booking_answers` (Roh-SQL) und reiht `mod_booking\task\check_answers` ein. Kollaborateure: `$DB`, `core\task\manager`, `core_component`, `singleton_service` (Settings + Answers). Der Klassen-Doc-Kommentar („cartstore class") ist ein kopierter, irrefuehrender Header.

## Methoden

### `public static function create_bookinganswers_check_tasks(int $contextid, int $check = self::CHECK_ALL, int $action = self::ACTION_DELETE, int $userid = 0)` — public static
- **Zweck:** Findet alle Buchungsoptionen unterhalb eines Kontextes und reiht pro Option einen Adhoc-Check-Task ein. **Seiteneffekte:** Gate auf `get_config('booking','unenroluserswithoutaccess')` UND `...areyousure)` (beide muessen aktiv sein, sonst frueher Return); ein `get_records_sql` (Options-Discovery via Kontext-`path LIKE`, optional auf `userid` und `waitinglist < 5` eingeschraenkt); pro Treffer `manager::queue_adhoc_task(new check_answers())` mit `custom_data` (optionid/check/action/userid). Ausfuehrungszeit: in PHPUNIT `time()`, sonst `+15 minutes`. **Bewertung:** B — sauberes Doppel-Settings-Gate und kontextbasierte Selektion; aber der Quellkommentar (Z.127) sagt „five minutes in the future", waehrend der Code `+ 15 minutes` ansetzt (Kommentar/Code-Diskrepanz, P3). Das verzoegerte Einreihen ist die bewusste Sicherung gegen unbeabsichtigte Massen-Loeschung.

### `public static function process_booking_option(int $optionid, int $check, int $action, int $userid = 0): array` — public static
- **Zweck:** Verarbeitet eine Option: laedt deren Answers, prueft jede (ggf. auf einen User eingeschraenkt) und fuehrt bei Fehlschlag die Action aus; gibt ein Log je User zurueck. **Seiteneffekte:** `singleton_service::get_instance_of_booking_option_settings` + `get_instance_of_booking_answers`; pro Answer `self::check_answer` und ggf. `self::perform_action` (datenmutierend ueber die Action). **Rueckgabe:** `array` Log keyed nach `userid` mit `['check' => …, 'action' => …]`. **Bewertung:** C — **stale-Variable-Bug:** `$actionresult` wird nur im `if (!empty($checkresult))`-Zweig gesetzt, aber im Log via `$actionresult ?? false` ausgelesen; da PHP die Variable ueber Schleifeniterationen hinweg behaelt, erbt eine Answer ohne fehlgeschlagenen Check faelschlich den `actionresult`-Wert der vorherigen Iteration (verfaelschtes Action-Logging; keine Datenloeschung, aber irrefuehrendes Audit-Log). P3. Zusatz: bei `$userid`-Filterung wird trotzdem die volle Answers-Liste geladen und in PHP gefiltert.

### `private static function check_answer(stdClass $answer, int $check, bool $breakonfirst = true): array` — private static
- **Zweck:** Fuehrt entweder alle Checks (`CHECK_ALL`) oder den per `$check` gewaehlten Check gegen die Answer aus und sammelt die IDs fehlgeschlagener Checks. **Seiteneffekte:** `core_component::get_component_classes_in_namespace('mod_booking','local\\checkanswers\\checks')`; `usort` nach statischer `$id`-Property der Check-Klassen; ruft `$checkclass::check_answer($answer)` (statisch). **Rueckgabe:** Liste fehlgeschlagener Check-IDs; bei `$breakonfirst` Abbruch nach dem ersten Fehlschlag. **Bewertung:** B — Discovery + Sortierung sauber; ein nicht behebbar fehlschlagender Check (z.B. fehlendes CM) fuehrt deterministisch zur Action. Die Klassen-Discovery pro Answer ist potenziell wiederholt teuer (kein Memo), bei vielen Answers pro Option leichte N+1-Tendenz auf Reflection-Ebene — in der Praxis durch core_component-Caching abgefedert. P3.

### `private static function perform_action(stdClass $answer, int $action): array` — private static
- **Zweck:** Findet die Action-Klasse mit passender `get_id()` und fuehrt sie aus. **Seiteneffekte:** `core_component::get_component_classes_in_namespace(... 'local\\checkanswers\\actions')`; ruft `$actionclass::perform_action($answer)` (datenmutierend). **Rueckgabe:** Liste erfolgreich ausgefuehrter Action-IDs. **Bewertung:** B — Discovery iteriert alle Action-Klassen und filtert per `get_id()`; korrekt, aber im Gegensatz zu `check_answer` ohne Sortierung (irrelevant, da nur ein Match erwartet).

## Bewertungs-Resümee
Solider, gut abgesicherter Orchestrator (Doppel-Settings-Gate, verzoegerte Adhoc-Tasks) mit sauberer core_component-Discovery von Checks und Actions. Schwachpunkte: der stale-`$actionresult`-Bug in `process_booking_option` (verfaelschtes Logging), die Kommentar/Code-Diskrepanz bei der Verzoegerung (5 vs. 15 Min.) und das In-PHP-Filtern der vollen Answers-Liste bei userspezifischen Laeufen. Da datenmutierend ueber `deleteanswer`, ist die Sicherungs-Schicht (Settings-Gate + Delay) zentral. Klassen-Score **B / P2**.
