## Klassenueberblick
`booking_bookit` ist der zentrale Orchestrator des gesamten Buchungs-/Reservierungs-Prozesses einer Buchungsoption. Es vereint zwei Aufgaben in einer statischen God-Call-Schnittstelle: (1) das **Rendering** des situationsabhaengigen bookit-Buttons bzw. eines Prepage-Modals/Inline-Containers/Alerts anhand der Blocking-Condition-Ergebnisse, und (2) den **Webservice-Einstieg** (`bookit`), der die Condition-Maschine ein zweites Mal mit `hardblock` befragt, daraus per langer if/else-Kaskade die naechste Prozess-Stufe ableitet (Bestaetigungs-Cache setzen, Credits abziehen, Storno/Reservierung/Elective-Reihenfolge verwalten) und schliesslich die eigentliche Antwort schreibt. Kollaborateure: `bo_availability\bo_info` (Condition-Ergebnisse + Sortierung), `output\renderer`/`prepagemodal`/`prepageinlinestart`/`bookit_button`/`bookingoption_description`, `booking_option` (Antwort-Persistenz), `price`, `singleton_service`, `booking_context_helper`, `bookit_request_overrides`, `cancelmyself`, `modechecker`, `elective`, `subbookings\subbookings_info` sowie der MUC-Cache `confirmbooking`/`electivebookingorder`. Persistenz indirekt ueber `booking_option` (`booking_answers`, Enrolment), Cache und Custom-Profile-Fields (Credits). Mutiert global `$PAGE`.

## Methoden

### `public static function render_bookit_button(booking_option_settings $settings, int $userid = 0, string $inlinestartpage = '')` — public static
- **Zweck:** Liefert den fertig gerenderten Button-/Modal-/Inline-HTML-String fuer eine Option. **Seiteneffekte:** liest `$PAGE`-Renderer (kein expliziter `set_context`, anders als `booking_subbookit::render_bookit_button`), delegiert die Template/Data-Ermittlung an `render_bookit_template_data` und rendert je nach Template-Name ueber den passenden Renderer-Aufruf (`render_prepagemodal`/`render_prepageinline`/`render_prepageinlinestart`/`render_bookit_button`). **Bewertung:** B — schlanke Dispatch-Schleife; einzige Schwaeche ist die implizite Reihenfolgenkopplung von `$templates` und `$datas` per `array_shift`.

### `public static function render_bookit_template_data(booking_option_settings $settings, int $userid = 0, bool $renderprepagemodal = true, string $inlinestartpage = '')` — public static
- **Zweck:** Kern der Rendering-Entscheidung: ermittelt aus `bo_info::get_condition_results()` welche Condition den Button stellt und ob ein Prepage-Modal/Inline-Container, ein Inline-Start oder ein direkter Button gerendert wird; liefert `[$templates, $datas]`. **Logik:** Switch ueber `$result['button']` (`MYBUTTON`, `MYALERT`, `NOBUTTON`, `JUSTMYALERT`, `CANCEL`); `MYALERT` wird bei `mod/booking:bookforothers` zum Zusatz-Button, sonst zum Hauptbutton mit unterdruecktem Modal; danach Sortierung via `bo_info::return_sorted_conditions`, optionaler Inline-Start-Pfad (`$inlinestartpage`), Modal/Inline-Container-Pfad oder direkter Button-Pfad inkl. cards-view-Sonderbehandlung (`turnoffmodals`). **Seiteneffekte:** mehrere `has_capability`-Pruefungen, `$PAGE->get_renderer` + `render_from_template` im Inline-Start-Zweig, `get_config('booking','turnoffmodals')`. **Bewertung:** D — sehr lange, mehrfach verschachtelte Methode mit mehreren Anti-Patterns: **`$buttoncondition` kann uninitialisiert verwendet werden** (`booking_bookit.php:301`/`:252` — liefern die Conditions weder MYBUTTON noch JUSTMYALERT, ist die Variable undefiniert beim `method_exists($buttoncondition,'instance')`); `$showinmodalbutton` wird gesetzt (`:125`/`:148`), aber **nie gelesen** (Dead Variable); `$templates` wird im else-Zweig erst per `[]`-Append auto-vivifiziert statt initialisiert. **Genuiner Bug:** die Bedingung `if (!empty($extrabuttoncondition && !empty($datas) && isset($data['main'])))` (`booking_bookit.php:312`) hat eine **falsch gesetzte Klammer** — das `!empty(...)` umschliesst den gesamten Booleschen Ausdruck statt nur `$extrabuttoncondition`; gemeint war offenkundig `!empty($extrabuttoncondition) && !empty($datas) && isset($data['main'])`.

### `public static function bookit(string $area, int $itemid, int $userid = 0, string $data = ''): array` — public static
- **Zweck:** Webservice-Einstieg fuers Buchen/Stornieren/Reservieren. Befragt fuer `area==='option'` `bo_info::is_available(..., hardblock=true, ..., $ignoredconditionids)` und leitet aus der zurueckgegebenen Blocking-Condition-`$id` per langer if/else-Kaskade die naechste Prozess-Stufe ab: Bestaetigungs-Marker im `confirmbooking`-Cache setzen (bookit/credits/subscription/confirmation), Credit-Abzug, Storno-Markierung (mit `cancelmyself`-Cooling-off), Elective-Reihenfolge im `electivebookingorder`-Cache; am Ende bei `$isavailable` echtes Buchen via `answer_booking_option(...BOOKED)`. **Seiteneffekte (umfangreich):** Capability-Pruefung gegen Modul- bzw. System-Context; **MUC-Cache-Writes/Deletes** (`confirmbooking`, `electivebookingorder`); **Custom-Profile-Field-Write** beim Credit-Abzug (`profile_save_custom_fields`, `booking_bookit.php:448`); DB-Writes ueber `answer_booking_option`. **Aufrufkette:** ruft `answer_booking_option` (BOOKED/DELETED/NOTBOOKED/RESERVED) und `answer_subbooking_option`. **Bewertung:** D — Monster-Methode (~280 Zeilen) mit hoher zyklomatischer Komplexitaet; der Autor markiert selbst `TODO: Refactor this` (`booking_bookit.php:386`). **Genuiner Bug:** im Zweig `CONFIRMBOOKWITHCREDITS` wird der Cache mit `$cache->set($userid, [...])` per `userid` befuellt, der Fehlerpfad bei zu wenig Credits ruft aber `$cache->delete($cachekey)` (`booking_bookit.php:440`) statt `delete($userid)` — **loescht den falschen Cache-Key**, der Bestaetigungs-Marker bleibt haengen. **Weiterer Bug:** der `area==='elective'`-Zweig bucht erfolgreich alle Optionen, gibt danach aber unkonditioniert `['status'=>0,'message'=>'novalidarea']` zurueck (`booking_bookit.php:610`) — meldet also Misserfolg trotz erfolgter Buchung. **Anti-Pattern:** `$cachekey` wird in mehreren Zweigen berechnet und dann gar nicht zum Loeschen verwendet (z. B. `:415` vs. `delete($userid)` `:416`). Rechte-Kommentar `more sophisticated way of rights management` deutet ein offenes Authorisierungs-Konzept an.

### `public static function answer_booking_option(string $area, int $itemid, int $status, int $userid = 0, bool $openruleexecution = false): array` — public static
- **Zweck:** Fuehrt die eigentliche Antwort-Operation aus und baut ein Shopping-Cart-Item-Array fuer die Option. **Status-Switch:** BOOKED/RESERVED → `user_submit_response` (reserved-Flag 0/1), NOTBOOKED → `user_delete_response($id, true)`, DELETED → `user_delete_response($id, false, false, true, false, $openruleexecution)`, NOTIFYMELIST → `toggle_notify_user`. **Seiteneffekte:** schreibt `booking_answers`/Enrolment via `booking_option`, holt Preis (`price::get_price`), **repariert global `$PAGE`-Context** (`booking_context_helper::fix_booking_page_context`), rendert eine Cart-Item-Beschreibung; liefert Item-Array (itemid/title/price/currency/description/imageurl/canceluntil/coursestarttime/courseendtime/**costcenter**). **Bewertung:** C — lange Methode mit Mehrfachverantwortung (Antwort-Mutation + Preis + `$PAGE`-Reparatur + Rendering + Item-Bau); `$area` ist **toter Parameter** (nie gelesen). **Duplikat-Befund:** nahezu wortgleich zur gleichnamigen Methode in `booking_subbookit::answer_booking_option`. Verifizierte Unterschiede: (a) diese Variante hat den **zusaetzlichen Parameter `$openruleexecution`**, den der DELETED-Zweig durchreicht (Subbookit-DELETED ruft nur `user_delete_response($id)`); (b) `MOD_BOOKING_DESCRIPTION_CARTITEM` statt `MOD_BOOKING_DESCRIPTION_WEBSITE`; (c) `get_instance_of_booking_by_optionid($itemid)` statt `_by_bookingid($settings->bookingid)`; (d) zusaetzliches Item-Feld `costcenter`; (e) der **auskommentierte Rechte-Check-Block** existiert nur in der Subbookit-Variante, hier nicht. Die Duplikation ist real und ein REFACTORING_BACKLOG-Kandidat (gemeinsamer Kern extrahieren, Varianten ueber Parameter steuern).

### `public static function answer_subbooking_option(string $area, int $itemid, int $status, int $userid = 0): array` — public static
- **Zweck:** Reserviert/speichert die Subbooking-Antwort und liefert das Cart-Item aus den Option-Settings. **Seiteneffekte:** `subbookings_info::save_response(...)` (kurzzeitige Reservierung waehrend Checkout), `return_subbooking_option_information`. **Bewertung:** B — schlank und klar delegierend; benoetigt `subbookings_info` + Option-Settings.

## Bewertungs-Resümee
`booking_bookit` ist der Dreh- und Angelpunkt von S01, leidet aber unter denselben Smells wie sein Subbooking-Pendant in verschaerfter Form: zwei extrem lange, hochverzweigte Methoden (`render_bookit_template_data`, `bookit`), globale `$PAGE`-Mutation, eine potenziell uninitialisierte `$buttoncondition`-Variable im Button-Switch, eine Dead Variable (`$showinmodalbutton`), ein toter Parameter (`$area` in `answer_booking_option`) und eine fast wortgleiche `answer_booking_option`-Duplikation mit `booking_subbookit`. Hinzu kommen **drei genuine Bugs**: die fehlplatzierte Klammer im `!empty(...)`-Guard (`:312`), das Loeschen des falschen Cache-Keys im Credit-Fehlerpfad (`:440`) und der irrefuehrende `status=0/novalidarea`-Return im Elective-Erfolgsfall (`:610`). Wegen Umfang, Komplexitaet und der Mehrzahl echter Defekte: Score **D / P1**; vorrangig sind der `bookit`-Refactor (der Autor selbst markiert ihn) und die De-Duplikation von `answer_booking_option`.
