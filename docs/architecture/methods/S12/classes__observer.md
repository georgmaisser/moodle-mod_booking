## Klassenueberblick
`mod_booking_observer` ist die zentrale Event-Observer-Klasse des Plugins und buendelt alle synchronen Reaktionen auf Moodle-Core-Events sowie auf plugin-eigene Events (`\mod_booking\event\*`) und Fremd-Plugin-Events (`local_shopping_cart`, `local_wunderbyte_table`). Saemtliche Methoden sind statisch und werden ueber die Registrierung in `db/events.php` an die jeweiligen Eventnamen gebunden; die Klasse haelt keinerlei eigenen Zustand. Ihre Verantwortung ist breit gefaechert: Cache-Invalidierung (`cache_helper::purge_by_event` / `invalidate_by_event`), Kalender-Synchronisation (`calendar`, `calendar_helper`), Aufraeumen von Buchungsdaten bei User-/Enrolment-Loeschung, Anstossen des Booking-Rules-Engines (`rules_info`), Aktivitaetsabschluss und Zertifikatsausstellung sowie Zwischenspeicher-Pflege fuer Wunderbyte-Tables und Custom-Forms. Wichtige Kollaborateure sind `singleton_service` (InstanzaufloEsung von Option/Settings/Answers), `booking_option`, `rules_info` (deferred-Execution via `$eventstoexecute`/`$rulestoexecute`), `checkanswers` (Ad-hoc-Tasks), `certificate_conditions`/`certificateclass` und `booking_enrolment` (Sync-Queue). Persistenz erfolgt teils direkt ueber `$DB` (Loesch-/Update-Queries auf `booking_answers`, `booking_teachers`, `booking_prices`, `event`, `booking_userevents` etc.), teils delegiert an Service-Objekte. Architektonisch auffaellig: ein Grossteil der Arbeit laeuft **synchron im Request des ausloesenden Events** und einige Handler enthalten potenziell teure SQL-Schleifen (N+1).

## Methoden

### `public static function user_created(\core\event\user_created $event)` — public
- **Zweck:** Prueft beim Anlegen eines neuen Users, ob Booking-Rules fuer ihn greifen. **Seiteneffekte:** ruft `rules_info::execute_rules_for_user($userid)` — kann je nach Regelsatz beliebig viele Folgeaktionen synchron ausloesen. **Aufrufkette:** `\core\event\user_created`. **Bewertung:** C — schlank, aber die Regel-Ausfuehrung haengt voll synchron am User-Anlegen; bei vielen Rules ein latentes Performance-Risiko.

### `public static function user_updated(\core\event\user_updated $event)` — public
- **Zweck:** Invalidiert Preis-Cache (Preise koennen von Profilfeldern abhaengen) und fuehrt Booking-Rules fuer den User aus. **Seiteneffekte:** `cache_helper::purge_by_event('setbackprices')` (globaler Preis-Cache-Purge), `rules_info::execute_rules_for_user`. **Aufrufkette:** `\core\event\user_updated`. **Bewertung:** C — der Purge des gesamten Preis-Caches bei *jedem* User-Update ist grobkoernig (vgl. MEMORY „grobe Purges"); bei haeufigen Profilaenderungen teuer.

### `public static function user_deleted(\core\event\user_deleted $event)` — public
- **Zweck:** Raeumt beim Loeschen eines Users alle seine Buchungsspuren aus 6 Tabellen weg. **Seiteneffekte:** `delete_records_select` auf `booking_answers`, `booking_history`, `booking_teachers`, `booking_optiondates_teachers`, `booking_userevents`, `booking_icalsequence` plus `cache_helper::purge_by_event('setbackcachedteachersjournal')` (`observer.php:96`-`102`). **Aufrufkette:** `\core\event\user_deleted`. **Bewertung:** C — funktional korrekt und privacy-relevant, aber harte `DELETE`s ohne Transaktionsklammer; bei Fehlern mittendrin bleiben halb geloeschte Zustaende. Kein Loeschen verknuepfter Kalender-`event`-Eintraege (anders als in `bookinganswer_cancelled`).

### `public static function user_enrolment_deleted(\core\event\user_enrolment_deleted $event)` — public
- **Zweck:** Beim Ausschreiben eines Users (nur bei `lastenrol`) loescht es dessen Antworten in Optionen von Booking-Instanzen mit `removeuseronunenrol=1` und seine Teacher-Eintraege; stosst zusaetzlich einen `checkanswers`-Task an. **Seiteneffekte:** Pro betroffener Option `booking_option::create_option_from_optionid()` + `user_delete_response()` (Schleife, `observer.php:122`-`125`), `delete_records_select` auf `booking_teachers`, `checkanswers::create_bookinganswers_check_tasks(...)`. **Aufrufkette:** `\core\event\user_enrolment_deleted`. **Bewertung:** D — **N+1-Muster** (`observer.php:122`): fuer jede Option wird ein vollstaendiges `booking_option`-Objekt erzeugt und `user_delete_response` synchron im Unenrol-Request ausgefuehrt; bei vielen Optionen pro Kurs teuer. Der `?? context_system::instance()`-Fallback (`observer.php:141`) ist toter Guard, da `context_course::instance()` bei ungueltiger Kurs-ID wirft statt `null` zu liefern.

### `public static function bookingoption_created(\mod_booking\event\bookingoption_created $event)` — public
- **Zweck:** Bewusst leerer Handler — Kalendererzeugung erfolgt ueber `bookingoption_updated`. **Seiteneffekte:** keine. **Aufrufkette:** `\mod_booking\event\bookingoption_created`. **Bewertung:** B — dokumentierter No-op; registriert, um die Semantik explizit zu halten.

### `public static function bookinganswer_cancelled(\mod_booking\event\bookinganswer_cancelled $event)` — public
- **Zweck:** Deferred-Aufraeumen der User-Events einer stornierten Antwort und Cache-Invalidierung der Option. **Seiteneffekte:** registriert eine Closure in `rules_info::$eventstoexecute`, die `booking_userevents` und die zugehoerigen `event`-Records loescht (`observer.php:177`-`181`); `cache_helper::invalidate_by_event('setbackoptionsanswers', [$optionid])`. **Aufrufkette:** `\mod_booking\event\bookinganswer_cancelled`. **Bewertung:** B — saubere Nutzung des deferred-Execution-Patterns; loescht im Gegensatz zu `user_deleted` auch die Kalender-`event`-Eintraege.

### `public static function checkout_completed(\local_shopping_cart\event\checkout_completed $event)` — public

Kleiner Inkonsistenz-Punkt: `componentname` mit `?? ''` abgesichert, `area` (`observer.php:198`) jedoch ohne Null-Coalescing-Guard.

### `public static function bookingoption_cancelled(\mod_booking\event\bookingoption_cancelled $event)` — public
- **Zweck:** Storniert beim Absagen einer ganzen Option alle Antworten der gebuchten User und loescht deren Kalender-User-Events; nutzt `$bookingoptioncancel=true`, um doppelte Stornomails zu vermeiden. **Seiteneffekte:** deferred Closure mit Schleife ueber alle gebuchten User: `user_delete_response($user->id, false, true)` + `calendar::delete_booking_userevents_for_option` (`observer.php:222`-`231`); sofort `booking_option::purge_cache_for_option`. **Aufrufkette:** `\mod_booking\event\bookingoption_cancelled`. **Bewertung:** C — korrekt und gut kommentiert, aber die User-Schleife (`user_delete_response` je User) laeuft synchron im deferred-Block und kann bei grossen Optionen lange dauern. PHPUNIT-Sonderzweig (`observer.php:216`) zeigt Testkopplung im Produktivcode.

### `public static function bookingoption_updated(\mod_booking\event\bookingoption_updated $event)` — public
- **Zweck:** Synchronisiert bei Optionsaenderung alle Optiondate-Kalenderevents, aktualisiert Teacher-Kalender, setzt Sichtbarkeit der Kalendereintraege und invalidiert den Optionscache. **Seiteneffekte:** Schleife `calendar_helper::option_optiondate_update_event` je Optiondate (`observer.php:251`-`254`); Schleife `new calendar(... MOD_BOOKING_TYPETEACHERUPDATE)` je Teacher (`observer.php:263`-`265`); `option_set_visibility_for_all_calendar_events`; **zwei** `booking_option::purge_cache_for_option`-Aufrufe (`observer.php:267` und `:278`). **Aufrufkette:** `\mod_booking\event\bookingoption_updated`. **Bewertung:** D — schwerer, voll synchroner Handler mit gleich zwei verschachtelten N+1-Schleifen (Optiondates × Teacher) und doppeltem Cache-Purge; der Kommentar „Tests will fail if removed" deutet auf fragile, nicht sauber verstandene Cache-Abhaengigkeiten hin.

### `public static function bookingoptiondate_created(\mod_booking\event\bookingoptiondate_created $event)` — public
- **Zweck:** Legt fuer ein neues Optiondate Kalendereintraege an — fuer die Option global, fuer jeden gebuchten User und fuer jeden Teacher. **Seiteneffekte:** Instanziierung mehrerer `calendar`-Objekte in zwei Schleifen ueber gebuchte User (`get_all_users_booked`, `observer.php:307`-`317`) und Teacher (`observer.php:319`-`328`). **Aufrufkette:** `\mod_booking\event\bookingoptiondate_created`. **Bewertung:** D — **N+1**: pro gebuchtem User und pro Teacher ein `new calendar(...)` mit jeweils eigenem DB-Write, synchron im Request, der das Optiondate erzeugt. Guard `if (empty($optionid)) return;` steht erst *nach* dem `singleton_service`-Aufruf (`observer.php:290`-`294`) — zu spaet, um nutzlose Arbeit zu sparen.

### `public static function bookingoptiondate_deleted(\mod_booking\event\bookingoptiondate_deleted $event)` — public

## Bewertungs-Resümee
Die Klasse erfuellt ihre Rolle als zentrale Event-Drehscheibe vollstaendig und ist im Kern korrekt: Cache-Invalidierungs- und Competency-Handler sind vorbildlich schlank (A/B), die Queue-basierten Membership-Sync-Handler nutzen sauber Ad-hoc-Tasks, und das deferred-Execution-Pattern ueber `rules_info::$eventstoexecute` ist gut eingesetzt. Der wiederkehrende Schwachpunkt liegt — wie schon im Perf-Audit der MEMORY notiert — im **synchronen Pro-Zeile-/Pro-Option-Aufwand**: `custom_field_changed` (`observer.php:423`-`450`, site-weites N+1, Score E), `bookingoption_updated` (`observer.php:251`-`265`, doppeltes N+1 + doppelter Purge, D), `bookingoptiondate_created` (`observer.php:307`-`328`, N+1 Kalender-Writes, D) und `user_enrolment_deleted` (`observer.php:122`, Option-Objekt je Schleife, D) sind die kritischen Hotspots. Hinzu kommen genuine Defekte/Anti-Patterns: verschluckte Exception ohne Message in `bookingoption_completed` (`observer.php:383`), Variable-Shadowing von `$event` in `course_completed` (`observer.php:515`), nutzloses `unset($columns['id'])` in `template_switched` (`observer.php:636`) sowie eingebaute `PHPUNIT_TEST`-Pfade im Produktivcode. Saubere Korrektheit, aber spuerbare Perf-Schuld und einige kleine Logik-/Robustheitsmaengel rechtfertigen **Klassen-Score C / P2**.
