# scheduledmails — Methoden-Doku

## Klassenueberblick
`scheduledmails` ist ein rein statischer Service rund um geplante (Adhoc-)Mails aus `task_adhoc`, die von `booking_rules` erzeugt wurden. Er (1) liefert DB-familien-bewusste SQL-Bausteine (`get_sql`), die `task_adhoc.customdata` per JSON-Extraktion mit `booking_rules` und `user` verknuepfen und nach Kontext filtern, (2) re-evaluiert die Gueltigkeit eines geplanten Mails gegen die aktuelle Rule-Logik (`is_task_still_valid`) und (3) bereinigt ungueltig gewordene Adhoc-Tasks anhand der gerenderten Tabelle (`cleanup_invalid_tasks_*`). Persistenz: liest/loescht `task_adhoc`, liest `booking_rules`/`user`. Kollaborateure: `$DB`, `rules_info::get_rule`, `scheduledmails_output`/`scheduledmails_table`, `cache_helper` (`scheduledmailscache` / `setbackscheduledmailscache`), `core_text`.

## Methoden

### `public static function get_sql($contextid = 1)` — public static
- **Zweck:** Baut die wunderbyte_table-SQL fuer die Scheduled-Mails-Uebersicht. Verzweigt nach `$DB->get_dbfamily()` zwischen Postgres- (`::jsonb ->>`) und MySQL-/Default-JSON-Extraktion (`JSON_UNQUOTE(JSON_EXTRACT(...))`) und extrahiert aus `task_adhoc.customdata` u.a. `ruleid`, `userid`, `optionid`, `cmid` sowie aus `booking_rules.rulejson` Name/Subject/Template. Joint `task_adhoc` -> `booking_rules` (ON `br.id = ruleid`) -> `user` (ON `u.id = userid`) und filtert per `LIKE`-Heuristik auf JSON-aehnliche Customdata mit `ruleid`. **Seiteneffekte:** liest nur `$DB->get_dbfamily()`. **Rueckgabe:** `[$fields, $from, $where, $params]` mit `$where = "s1.contextid = :scheduledmailscontextid"` (kontextgefiltert). **Bewertung:** C — funktional, aber mehrere Vorbehalte: der `user`-INNER-JOIN verwirft stillschweigend Tasks mit unbekanntem/geloeschtem User; bei MySQL liefert `JSON_UNQUOTE(JSON_EXTRACT(...))` fuer `ruleid` einen String, der gegen das numerische `br.id` gejoint wird (Implicit-Cast, kann Indexnutzung verhindern); der `else`-Zweig ist als "MySQL" kommentiert, deckt aber jede Nicht-Postgres-Familie ab (z.B. sqlsrv) ungetestet. Parameterisierung ist sauber (nur `:scheduledmailscontextid`), kein Injection-Vektor.

### `public static function is_task_still_valid(stdClass $values): bool` — public static
- **Zweck:** Prueft, ob ein geplantes Mail laut aktueller Rule-Logik noch zutrifft. Validiert Pflichtfelder, decodiert `customdata`, baut aus `taskdata` ein Rule-Instanz-Surrogat, vergleicht — falls vorhanden — die zum Task gespeicherte `rulejson` als dekodiertes Objekt gegen die aktuelle (Drift-Erkennung), holt die Rule via `rules_info::get_rule(rulename)` und ruft `check_if_rule_still_applies(optionid, userid, nextruntime, optiondateid)`. **Seiteneffekte:** keine DB-Schreibzugriffe; `rules_info::get_rule` (kann Rule-Registry/Cache anstossen); faengt jedes `\Throwable` ab. **Rueckgabe:** `bool` (defensiv `false` bei jeder fehlenden Voraussetzung oder Exception). **Bewertung:** B — robuste Fail-closed-Semantik (jede Unsicherheit -> ungueltig). Kleiner Konsistenz-Vorbehalt: `rulename`/`rulejson` werden aus `taskdata` gelesen, nicht aus den per `get_sql` projizierten `br.*`-Spalten — Tasks ohne diese Felder in der Customdata gelten pauschal als ungueltig (siehe Cleanup-Folgen). Object-Vergleich (`!=`) statt String-Vergleich vermeidet DB-Formatierungsunterschiede — gut.

### `public static function cleanup_invalid_tasks_in_context(int $contextid, int $pagesize = 100000): array` — public static
- **Zweck:** Convenience-Einstieg: baut die `scheduledmails_output`-Tabelle fuer einen Kontext und delegiert die eigentliche Bereinigung an `cleanup_invalid_tasks_from_table`. **Seiteneffekte:** instanziiert `scheduledmails_output($contextid)` + `return_table()`. **Rueckgabe:** Statistik-Array (durchgereicht). **Bewertung:** A — duenner Adapter.

### `public static function cleanup_invalid_tasks_from_table(scheduledmails_table $table, int $pagesize = 100000): array` — public static
- **Zweck:** Bereinigt ungueltige Adhoc-Tasks anhand der *gerenderten* Tabellenzeilen: rendert bis `$pagesize` Zeilen (`printtable`), iteriert `formatedrows`, liest die formatierte `status`-Spalte (Tags gestrippt, lowercased) und loescht den Task (`task_adhoc.id = $key`) genau dann, wenn der Status dem lokalisierten "No" entspricht. Zaehlt geprueft/geloescht/ohne-Status/ohne-Task-id. **Seiteneffekte:** `$table->printtable(...)`; pro Treffer `$DB->delete_records('task_adhoc', ['id' => $taskid])`; abschliessend `cache_helper::purge_by_definition('mod_booking', 'scheduledmailscache')` + `purge_by_event('setbackscheduledmailscache')`. **Rueckgabe:** `['checked', 'deleted', 'nostatusfound', 'notasksfound']`. **Bewertung:** C — die Loeschentscheidung haengt am *gerenderten, lokalisierten* Status-String der Tabellenspalte (Vergleich gegen `get_string('no')`). Das koppelt eine destruktive `task_adhoc`-Loeschung an Praesentations-/Lokalisierungslogik: aendert sich die Status-Spalten-Formatierung oder die Sprache zur Renderzeit, kann die Heuristik kippen. `$pagesize`-Default 100000 ist Speicher-/Render-intensiv. Innerhalb des Designs (Status = Ergebnis von `is_task_still_valid`) korrekt, aber fragil.

## Bewertungs-Resümee
Nuetzlicher, DB-familien-bewusster Service mit fail-closed Gueltigkeitspruefung. Hauptrisiken sind architektonisch: `cleanup_invalid_tasks_from_table` trifft eine destruktive Loeschentscheidung anhand des gerenderten, lokalisierten Status-Strings (Kopplung Praesentation->Loeschung), und `get_sql` verwirft per INNER-JOIN Tasks mit unbekanntem User bzw. casted ruleid implizit. Keine Injection. Klassen-Score **C / P2**.
