## Klassenueberblick
`executerestscript` ist der komplexeste bo_action-Typ (erweitert `booking_action`). Er ruft nach einer Buchung/Storno ein externes REST-Script per cURL-POST auf — entweder als klassischen Form-Field-POST oder, wenn ein JSON-Body-Template konfiguriert ist, als JSON-Request mit `{placeholder}`-Substitution ueber das mod_booking-Placeholder-Framework. Erfolg/Misserfolg werden als Events (`rest_script_success`/`rest_script_failed`) geloggt. Die Klasse haelt keinen Zustand; Persistenz erbt sie aus `booking_action::save_action`. Kollaborateure: `singleton_service` (Settings/User/Booking-Answers), `placeholders_info::render_text`, `baid`-Placeholder, `$DB` (booking_answers), cURL, `context_module`, Event-API.

## Methoden

### `public function apply_action(stdClass $actiondata, int $userid = 0)` — public
- **Zweck:** Ermittelt die relevante Buchungsantwort und stoesst den REST-Call an, dann triggert es ein Erfolgs-/Fehler-Event. **Seiteneffekte:** liest Option-Settings; bevorzugt die per `$actiondata->baid` adressierte Antwort direkt aus `{booking_answers}` (funktioniert auch bei Storno, wo die Antwort soft-deleted und nicht mehr in `get_usersonlist()` ist); Legacy-Fallback ueber die aktive Antwortliste; bei vorhandener Antwort externer cURL-Call via `get_script_response` und `rest_script_success`/`rest_script_failed`-Event (mit JSON-serialisierter Antwort und Aktionsdaten im `other`). **Rueckgabe:** `int` 0 — erlaubt folgende After-Actions. **Bewertung:** B — der baid-zentrische Lookup ist die korrekte Loesung fuer den Storno-Fall (gut dokumentiert). Schwaeche: das Erfolgs-Event speichert die komplette REST-Antwort und die ganze Aktion (inkl. evtl. `secrettoken`) im Event-Log (`other`), was sensible Daten persistiert.

### `public static function get_script_response($bookinganswer, $actiondata)` — public static
- **Zweck:** Baut die Request-Parameter aus der Buchungsantwort und den Aktionsdaten, fuehrt den cURL-POST aus und gibt die rohe Antwort zurueck. **Seiteneffekte:** `json_decode($bookinganswer->json)` → `condition_customform`-Felder; optional User-Daten (firstname/lastname/email/username) bei aktiviertem `userparameter`; Header-Aufbau; bei JSON-Body individuelle Placeholder-Substitution via `preg_replace_callback('/\{(\w+)\}/', ...)` mit `baid::$baid`-Seeding und `placeholders_info::render_text`; **externer Netzwerkaufruf** per `curl_exec`. **Rueckgabe:** `string|bool` cURL-Response (false bei Fehler). **Bewertung:** D — mehrere Probleme: (1) der Debug-Header `'Cookie: XDEBUG_SESSION=VSCODE'` wird bei JEDEM externen Call mitgesendet (Entwicklungs-Artefakt, leakt an Fremdsysteme); (2) `if (!empty($actiondata->userparameter == '1'))` ist ein verfehltes Idiom — `empty()` auf einen bereits ausgewerteten Boolean; funktioniert nur zufaellig wie `($x == '1')`; (3) `CURLOPT_TIMEOUT => 0` = unbegrenzt → ein haengender Endpoint blockiert den Buchungs-Request unbegrenzt; (4) `$info`/`$error` werden ausgelesen, aber nie verwendet (toter Code, kein Logging des HTTP-Status). Die JSON-Placeholder-Logik selbst ist sorgfaeltig und ausfuehrlich kommentiert (umgeht den nicht-JSON-faehigen `{(.*?)}`-Matcher korrekt).

### `public static function add_action_to_mform(&$mform)` — public static
- **Zweck:** Baut das Aktions-Formular: Script-URL, numberofdays, secrettoken, mehrere advcheckboxen (customform-/admin-/userparameter), customheaders-Textarea, jsonbody-Textarea und sslverify. **Seiteneffekte:** mutiert `$mform`; Typisierung (`PARAM_URL`/`PARAM_INT`/`PARAM_TEXT`/`PARAM_RAW`). **Rueckgabe:** void. **Bewertung:** C — `sslverify` ist per Default AUS, d.h. Standardverhalten sendet User-Daten (email/name) ohne TLS-Zertifikatspruefung (MITM-Risiko, bewusst als rueckwaerts-kompatibel dokumentiert). Das `adminparameter`-Feld wird angeboten, in `get_script_response` aber nie ausgewertet (toter Schalter).

### `public static function validate_action_form($data)` — public static
- **Zweck:** Validiert das Formular; prueft, dass `numberofdays` numerisch ist. **Seiteneffekte:** keine. **Rueckgabe:** `array` der Feld-Fehler. **Bewertung:** B — funktioniert, aber `!is_null($value)` greift nie auf fehlende Keys (iteriert nur vorhandene `$data`-Keys); keine Validierung von URL/Headers/JSON-Body. Ausreichend, aber duenn.

## Bewertungs-Resümee
Funktional maechtigster Aktionstyp und zugleich der riskanteste: externer cURL-Aufruf mit hartem XDEBUG-Cookie-Header, unbegrenztem Timeout, standardmaessig deaktivierter TLS-Verifikation und Persistenz potenziell sensibler Daten (secrettoken, REST-Antwort) im Event-Log. Die JSON-Placeholder-Substitution ist hingegen sauber und gut begruendet. Klassen-Score **C / P2**.
